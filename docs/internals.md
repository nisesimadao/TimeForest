# 内部メモ — TimeTree 内部 API のリバースエンジニアリング

TimeTree に公開 API は無いので、Web アプリが叩いている内部 API に相乗りしている
（高レベルの概要は [README の「仕組み」](../README.md#仕組み)）。ここはその内部 API と
データモデルを **実測で** 解いた詳細 — 使うだけなら読まなくてよく、書き込みや繰り返し
予定に手を入れるコントリビュータ向けの資料。

## 繰り返し予定の書き込み

**「この回だけ編集」のためのエンドポイントは無い。** 繰り返しの編集は、親の
`recurrences` を書き換える操作と、必要なら親を指す別イベントを足す操作の
組み合わせでできている。

以下は全部、**TimeTree 自身の Web アプリを捨てアカウントのセッションで動かし、
その UI を実際に操作して、送信内容を捕捉した**もの。推測ではない。

| 操作 | 送るもの |
| --- | --- |
| この回だけ編集 | `POST /event` に **`parent_id: <親uuid>`** と `silent: true` → 子ができる<br>`PUT /event/{親}` `{recurrences: [RRULE, EXDATE:<その回>], silent: true}` |
| これ以降を編集 | `POST /event` に `recurrences: [RRULE]` と `copy: true` → 分割点から新しい親<br>`PUT /event/{親}` `{recurrences: [RRULE;UNTIL=<最後に残す回>]}` |
| すべてを編集 | `PUT /event/{親}` に変更分だけ |
| この回だけ削除 | `PUT /event/{親}` `{recurrences: [RRULE, EXDATE:<その回>]}` |
| これ以降を削除 | `PUT /event/{親}` `{recurrences: [RRULE;UNTIL=<最後に残す回>]}` |
| すべて削除 | `DELETE /event/{親}` |

推測では辿り着けなかった点が3つある:

- **`parent_id` が親子リンクの書き込み側の名前。** 読み取りでは同じ関係が
  `recurring_uuid` として返ってくるが、`recurring_uuid` を送っても**黙って
  無視される**（作成でも PUT でも、echo も読み戻しも `null`）。`parent_id` を
  送るとサーバーが両方を設定する
- **`silent: true`** は「この回だけ編集」の 2 リクエストに付く。ユーザーには
  1つの行為でも、サーバーには 2つの書き込みになる。共有カレンダーで
  メンバーに通知が二重に飛ぶのを抑えているものと思われる
- **`UNTIL` は日付のみで、「最後に残す回の表示日」。** 分割点の前日ではない。
  しかも EXDATE で穴が空いていると「1周期前」とも一致しない（実測: 8/10 と
  8/17 を消した状態で 8/24 から分割 → `UNTIL=20260803`）。だから展開器に
  「その回の前の回」を訊いて決めるしかない

## データモデルの罠

実データ（2395件）を TimeTree 自身の月表示と突き合わせて判明したもの。
これを踏まないと表示がズレる:

| 罠 | 内容 |
| --- | --- |
| `deactivated_at != null` | 削除済み。除外する |
| `category: 2` | **カレンダーの予定ではなく「メモ(Keep)」**。`row_order` を持つ。グリッドには出ない |
| `type: 1` | 誕生日。`title` は空で返る。`author_id` → メンバー名で `🎂 ◯◯の誕生日` を組み立てる |
| 繰り返し | 親が `RRULE` + `EXDATE` を持ち、変更された回は EXDATE で穴を空けて `recurring_uuid` を持つ別イベントとして再登録される（「【休】そろばん教室」がこれ） |
| 終日の `end_at` | **含む**。7/1〜7/3 は3日間。iCal の `DTEND` は含まないので ICS 出力時に +1日する |
| 複数日 | 終日とは限らない。時刻付きが日をまたぐこともある（8/8 21:00 → 8/16 22:00） |
| 祝日 | events API に**入っていない**。`memorialdays` から別途取得してマージ |

RRULE は実際のデータでは `FREQ=DAILY|WEEKLY|YEARLY` + `BYDAY` / `UNTIL` /
`INTERVAL` しか使われていない（`BYMONTHDAY` も `BYSETPOS` も皆無）。なので
rrule.js は入れず、`src/lib/recur.js` に小さな展開器を自前で持っている。

`COUNT` もそのサンプルには無かったが、**書き込み API は `COUNT` を受け付けて
保存する**（実測）。つまり本家アプリやこのクライアントが作れるので、無視は
できない。無視していた頃は、2020年に5回で終わった週次シリーズが2020年に52件
展開され、2026年にもまだ描画されていた。`COUNT` はシリーズ自身の開始からの
本数であって、描画している窓からの本数ではない — だから窓の外の回も、EXDATE が
後で落とす回も数える必要がある（RFC 5545: EXDATE は COUNT が既に決めた集合から
引く）。`scripts/check.js` が展開器を実際に呼んでこれを守っている。

## 検証

`src/lib/recur.js` の展開結果を、TimeTree が実際に描画した月グリッドと突き合わせ
済み（2026年7月）。**104/107 が完全一致**し、残りの差分もすべて説明がつく:

- 七夕・海の日 → events API 由来ではない（memorialdays でマージして解決）
- 誕生日2件 → タイトル空で返る仕様（author_id から合成して解決）
- 西公民館に700円持参 → `category: 2` のメモ（除外して解決）
